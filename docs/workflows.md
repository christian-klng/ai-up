# Workflows & MCP

Technische Referenz zum „Maschinenraum“. Nutzersicht: Verwaltung → Workflows / LLM / Fragen / API-Schlüssel.

## Workflow-Engine

- Definitionen (Trigger + Schritte) liegen in `workflows` (JSON), jede Änderung als Version in `workflow_versions`; Läufe in `workflow_runs` / `workflow_run_steps`.
- Registry: `src/server/workflows/triggers` (content.created, content.updated, schedule, manual, question.answered, llm.error, member.registered, member.approved, meeting.started, meeting.ended, meeting.recording.available) und `src/server/workflows/actions` (llm, transcribe, set_meeting_transcript, read_webpage, notify_user, send_message, create_content, ask_user). Neue Trigger/Aktionen = eine Datei mit zod-Schema, Feldbeschreibung (de/en) und `run()`. `create_content` legt Einträge über die System-Vorlagen an (Typ `structured` mit Vorlagen-Snapshot; Config `type: markdown|link` unverändert), der `content.created`-Trigger sieht entsprechend `type: "structured"`.
- Ausführung im **Worker** (`npm run worker`, BullMQ-Queue `workflow-runs`); Zeit-Trigger als BullMQ Job Scheduler, Abgleich bei jeder Workflow-Änderung und beim Worker-Start.
- Templates: LiquidJS – `{{ trigger.* }}`, `{{ steps.<id>.output.* }}`, `{{ app.name }}`, `{{ app.purpose }}`.
- LLM: OpenAI-kompatible Provider unter Admin → LLM (Schlüssel AES-256-GCM-verschlüsselt mit `APP_ENCRYPTION_KEY`); Structured Output über `response_format` mit Fallback-Parsing.
- Trigger `llm.error`: startet, wenn ein Aufruf an ein Sprachmodell fehlschlägt – in einem Workflow-Schritt, einer Eintrags-Bewertung, einem Agenten-Zug oder einer Transkription (`src/server/llm/errors.ts`). **Gedrosselt auf ein Ereignis je Provider+Modell alle 10 Minuten**, sonst startet ein Ausfall Dutzende Läufe. Filter: Provider und Teiltext der Meldung. Vorsicht beim Bauen: Ein Workflow, der darauf reagiert, sollte nicht selbst denselben Provider aufrufen – der Schleifenschutz (gleicher Workflow) und `MAX_DEPTH` fangen das, aber eine Benachrichtigung ist die bessere Reaktion als ein weiterer LLM-Aufruf.
- Realtime-Events `workflow.run.started/finished` → Toasts oben rechts (min. 2 s), Fehler-Notifications an Admins.
- Aktion `send_message`: Chat-Nachricht vom **System-Bot** (Name und Bild unter Verwaltung → KI-Agenten) an Empfänger; die Bot-Unterhaltung erscheint ohne Kontaktanfrage im Messenger. Sie ist **empfangsseitig** – Mitglieder können dem Bot nicht antworten (Guard in `sendMessage`, `src/server/domain/messenger.ts`); für Dialoge ist der KI-Agent da (siehe `docs/ki-agenten.md`).
- Aktion `ask_user`: erzeugt eine Frage (Umfrage/Bewertung/CTA), die Mitgliedern unten links als Mini-Formular erscheint; Antworten feuern den Trigger `question.answered` (Filter `questionKey`). Auswertung unter Verwaltung → Fragen.
- Aktion `transcribe`: Speech-to-Text für eine `media_files`-Datei über den OpenAI-kompatiblen Endpunkt `/audio/transcriptions` des gewählten LLM-Providers (OpenAI `whisper-1`/`gpt-4o-transcribe`, Groq, eigenes Whisper – **nicht** OpenRouter). Max. 25 MB pro Datei, Ausgabe `text`/`markdown` (mit Zeitmarken)/`segments`. Typische Kette: Trigger `meeting.recording.available` → `transcribe` (`{{ trigger.mediaId }}`) → `llm` (Zusammenfassung) → `set_meeting_transcript` (schreibt `meetings.transcript_markdown`, erscheint einklappbar auf der Meeting-Seite; `mode: "append"` (Default) hängt bei vorhandenem Transkript einen datierten Abschnitt an – z. B. nach Wiedereröffnen und zweiter Aufnahme –, `mode: "replace"` überschreibt) → `notify_user`/`create_content`.

## KI-Agenten

Eigene Doku: `docs/ki-agenten.md`. Für den Maschinenraum relevant: Agenten-Turns laufen als vierte Job-Art `{kind:"agent-turn"}` in derselben BullMQ-Queue wie Workflow-Läufe, Zeitpläne und Eintrags-Bewertungen. Die Werkzeuge liegen in einer eigenen Registry (`src/server/agents/tools/`) und rufen dieselben Domänenfunktionen wie MCP – die Dopplung zur MCP-Schicht ist bewusste, dokumentierte Schuld (siehe `docs/ki-agenten.md`, 1.9).

## MCP-Server

- Endpunkt `POST /api/mcp` (Streamable HTTP, stateless), Auth `Authorization: Bearer aiup_…` **oder** `x-api-key: aiup_…` (API-Schlüssel unter Verwaltung → API-Schlüssel; nur Admins, Scopes `workflows:read|write`, `runs:read|trigger`, `llm:read|write`, `questions:read`, `landing:read|write`, `knowledge:read|write`).
- Sammlungen per MCP (`knowledge:read|write`): `list_collections`, `list_templates`, `get_template`, `validate_structure`, `save_template`, `set_template_evaluation`, `delete_template`, `set_collection_templates`, `list_entries`, `get_entry`, `create_entry`, `update_entry`. Format und Regeln liefert die dynamische Resource `aiup://docs/collections`. `create_entry` verlangt `template` (Id oder systemKey) plus `answers` (Element-Key → Antwort, validiert wie im UI); der Shortcut `type: markdown|link` mappt auf die System-Vorlagen und umgeht die Zuweisungsprüfung (für Automation). `update_entry` mit `upgrade: true` hebt einen Eintrag auf die aktuelle Vorlagen-Version. Autor ist der Schlüssel-Inhaber. `set_template_evaluation` setzt die LLM-Prüfkriterien einer Vorlage (auch für System-Vorlagen) und kann mit `recheck: true` alle bestehenden Einträge neu prüfen lassen; `get_entry` liefert die Urteile der aktuellen Version mit. Bild-/Video-Uploads lassen sich nicht per MCP anlegen (nur URL-Varianten). `x-api-key` ist für claude.ai-Custom-Connectors gedacht: Dort ist der `Authorization`-Header für OAuth reserviert, im Dialog unter „Request headers" also `x-api-key` mit dem rohen Schlüssel (ohne „Bearer") eintragen.
- Tools: `list_triggers`, `list_actions`, `describe_action`, `describe_trigger`, `list_llm_providers`, `list_llm_models`, `list_workflows`, `get_workflow`, `validate_workflow`, `create_workflow`, `update_workflow`, `set_workflow_status`, `delete_workflow`, `list_runs`, `get_run`, `trigger_workflow`, `get_workflow_stats`, `list_questions`, `get_question_results`, `get_page`, `validate_page`, `update_page`, `list_page_versions`, `restore_page_version`, `set_page_enabled`, `list_page_media`. Resources `aiup://docs/workflow-schema`, `aiup://docs/pages`, `aiup://docs/model-capabilities`.
- Modell-Fähigkeiten (`llm:read|write`): `list_model_capabilities` (Tabelle **plus** die freigeschalteten Modelle *ohne* Eintrag – das ist die Arbeitsliste), `set_model_capabilities` (Massen-Upsert, Merge-Semantik: weggelassenes Feld behält den gespeicherten Wert, `null` löscht ihn; `source` ist Pflicht und sollte die Hersteller-Doku sein), `delete_model_capabilities`. Format und Regeln liefert die Resource `aiup://docs/model-capabilities`. Typischer Pflege-Satz in Claude: „Aktualisiere die Modell-Fähigkeiten für <Anbieter> aus <Doku-URL>". Hintergrund in `docs/modell-faehigkeiten.md`.
- Webseiten (`landing:read|write`): drei öffentliche Seiten `landing` (/), `imprint` (/imprint), `privacy` (/privacy) mit gemeinsamem Sektions-Schema (zod-validiert), je Seite eigener Aktivierung und Versionierung (`landing_page_versions.page`) und einem gemeinsamen Bild-Pool. Design-Regeln + aktuelle App-Variablen liefert die dynamische Resource `aiup://docs/pages`. Aktivierung unter Verwaltung → Webseiten oder per `set_page_enabled`.
- Claude Code: `claude mcp add --transport http aiup https://<domain>/api/mcp --header "Authorization: Bearer <KEY>"`.
