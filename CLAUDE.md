# AI-Up – Projekthinweise

- Plan & Phasen: `PLAN.md` (Abschnitt 11 = Reihenfolge; Stand siehe `README.md`). Entwickler-Doku: `docs/entwicklung.md`, Workflows/MCP: `docs/workflows.md`, Meetings/LiveKit: `docs/meetings-livekit.md`.
- Sprache: UI-Texte immer in `messages/de.json` **und** `messages/en.json` pflegen (next-intl, kein URL-Prefix, Cookie `aiup_locale`). Achtung ICU: keine `{{ }}`/`<tag>` in Übersetzungsstrings (bricht das Message-Format). Code, Kommentare, MCP-Felder, Trigger-/Aktions-IDs, LLM-Instruktionen: Englisch; Labels dazu `{ de, en }`.
- Auth: Better Auth (nur Magic Link). Registrierung ist ein eigener Flow (`registerUser`, Status `pending`); Guards über `requireUser()/requireAdmin()` (Pages) bzw. `assertUser()/assertAdmin()` (Server Actions). `src/proxy.ts` ist nur ein Cookie-Gate, keine Autorisierung. MCP-Auth: API-Keys (`src/server/domain/api-keys.ts`, Scopes).
- MCP-Konnektor einrichten: Endpunkt `https://ai-up.club/api/mcp` (Streamable HTTP, zustandslos, `src/app/api/mcp/route.ts`). In der Connector-UI von Claude (Einstellungen → Connectors → Custom Connector) als Request-Header **`x-api-key: aiup_…`** eintragen – **nicht** `Authorization`, das ist dort für OAuth reserviert (per CLI ginge auch `Authorization: Bearer aiup_…`). Der Schlüssel muss die Scopes der genutzten Tools tragen (z. B. `knowledge:read|write` für Sammlungen); fehlt einer, antwortet jedes Tool mit `API key lacks scope "…"`. Klartext gibt es nur beim Anlegen, in der DB liegt nur der Hash – sonst neuen Schlüssel unter *Verwaltung → API-Schlüssel* anlegen.
- DB: Drizzle, Schema in `src/server/db/schema.ts`, Spalten snake_case (casing). Nach Schemaänderung: `npm run db:generate` (Migration committen) und `npm run db:migrate`. Korrelierte Subqueries: Spalten explizit qualifizieren (`${table}."col"`).
- Medien: nie überschreiben – neue `media_files`-Zeile pro Version; Auslieferung über `/api/files/:id`; Upload nur über `/api/upload` (Magic-Bytes-Prüfung). Nutzer-URLs nur über `safeFetch` (SSRF-Schutz).
- Events: Fachlogik emittiert Domain-Events über `emitDomainEvent()` (`src/server/events/bus.ts`); der Bus ruft den Workflow-Dispatcher auf. Realtime an Clients ausschließlich über `publishToUser/publishBroadcast` (`src/server/realtime/publish.ts`, Typen in `src/lib/realtime-events.ts`); Client-Abos per `useRealtimeEvent()`.
- Workflows: neue Trigger/Aktionen als Registrierung in `src/server/workflows/triggers|actions/index.ts` (zod-Config, `fields` für den Editor, englisches `doc`, `run()`); Templates sind LiquidJS. Seiteneffekte aus Workflows mit `origin: { kind: "workflow" }` taggen (Schleifenschutz). System-Bot: `src/server/domain/bot.ts` (`BOT_USER_ID`), Bot aus Nutzerlisten/Audiences ausschließen (`users.isBot`). Name, Bild, Provider/Modell und Limits des Bots liegen in `ai_agents` (System-Agent, `SYSTEM_AGENT_ID`, `src/server/domain/agents.ts`, Verwaltung → KI-Agenten) und werden von `ensureBotUser()` auf die `users`-Zeile gespiegelt – `app_settings.botName` ist nur noch Seed-Quelle. Die Bot-Unterhaltung im Messenger ist **empfangsseitig**: `sendMessage()` weist Nachrichten an den Bot ab, Dialoge laufen über die KI-Agenten (`docs/ki-agenten.md`).
- Webseiten (Admin → „Webseiten", Route `/admin/pages`): drei öffentliche Seiten `landing` (`/`), `imprint` (`/imprint`), `privacy` (`/privacy`) mit gemeinsamem Sektions-Schema (`src/lib/landing-schema.ts`, `SITE_PAGES`), je Seite eigenem Enabled-Flag in `app_settings` und append-only-Versionen in `landing_page_versions` (Spalte `page`; `src/server/domain/landing.ts`, Restore = Copy-forward). `/` entscheidet über Landing oder Redirect (`/login` bzw. `/home`); Impressum/Datenschutz liefern 404, solange deaktiviert. Die eingeloggte Startseite liegt auf **`/home`** – Redirect-/Link-Ziele nie auf `/` zeigen lassen. MCP: Scopes `landing:read|write`, Tools `get_page`/`update_page`/`set_page_enabled`/…, Regeln + aktuelle App-Variablen liefert die dynamische Resource `aiup://docs/pages`. Seiten-Bilder haben `purpose: "landing"` (ein gemeinsamer Pool) und sind öffentlich (`/api/files`).
- Sammlungen: UI-Begriff für die früheren „Wissensbereiche" – **nur** die Anzeige wurde umbenannt; Routen (`/knowledge`), Tabellen (`knowledge_areas`), Code-Bezeichner und Workflow-Config-Keys (`areaId(s)`) bleiben. Inhalte entstehen über **Vorlagen** (`content_templates` + Versions-Snapshots, Zuweisung pro Sammlung in `knowledge_area_templates`; ohne Zuweisung gelten die geseedeten System-Vorlagen `text|image|link|video` – nicht editier-/löschbar, `src/lib/structures/defaults.ts` ist maßgeblich, Seed bumpt Versionen). Definition/Validierung/Markdown-Renderer/Antwort-Migration in `src/lib/structures/` (pure TS, auch Worker-tauglich – keine `next/*`-Imports); Elementtypen inkl. `markdown`/`image`/`link`/`video` (Media-Antworten `{mediaId?|url?}`; `markdown` mit `multiple: true` = Akkordeon-Liste, Antwort `[{title, body}]`; unreine Anreicherung wie Link-Previews liegt in `meta.structure.enrichment`, berechnet in `src/server/domain/structured-entries.ts` – dem gemeinsamen Schreibpfad für Action, MCP und Worker). Neue Einträge sind immer Typ `structured` und speichern Antworten **plus vollen Definitions-Snapshot** in `content_versions.meta.structure`; editiert wird gegen den Snapshot, ein Upgrade auf die aktuelle Vorlagen-Version ist opt-in beim Bearbeiten (`migrateStructureAnswers`). `bodyMarkdown` wird deterministisch generiert, Suche/Verlauf/Diff laufen darauf. Alt-Einträge freier Typen bleiben über den Edit-Pfad von `saveContentAction` pflegbar (kein Create mehr). MCP: Scopes `knowledge:read|write` (Tools `list_collections`/`list_templates`/`save_template`/`set_collection_templates`/`create_entry`/…, Regeln in Resource `aiup://docs/collections`). Die Sammlung selbst legt MCP **nicht** an – es gibt kein `create_collection`; neue Sammlungen entstehen nur über *Verwaltung → Sammlungen* (`/admin/knowledge`), erst danach greifen `create_entry` & Co.
- Evaluation von Einträgen: Jede Vorlage kann qualitative Kriterien tragen (`content_templates.evaluation`: `{providerId, model, criteria:[{key,title,instruction}]}`, Typen/Validierung in `src/lib/structures/evaluation.ts`). Sie sind **nicht** Teil des Definitions-Snapshots – die aktuellen Kriterien gelten immer für alle Einträge. Nach jedem Speichern eines strukturierten Eintrags reiht `createContent`/`addContentVersion` einen BullMQ-Job (`{kind:"evaluate"}`, JobId `eval-<versionId>`) ein; der Worker prüft in `src/server/domain/evaluation.ts` **je Kriterium einen eigenen LLM-Call** (JSON `{passed, reason}`, max. 3 parallel) und schreibt je (Version, Kriterium) eine Zeile in `content_evaluations` (`pass|fail|error`). Ergebnis kommt per Realtime `content.evaluation.updated` in die Popover-Anzeige neben „Bearbeiten". Kriterien ändern zählt die Vorlagen-Version **nicht** hoch (nur Definitionsänderungen tun das); bestehende Einträge behalten ihr Urteil bis zum nächsten Speichern oder einem manuellen „Alle neu prüfen". Für System-Vorlagen laufen Kriterien über `setTemplateEvaluation`/`saveTemplateEvaluationAction` bzw. MCP `set_template_evaluation` (Definition bleibt seed-verwaltet).
- KI-Agenten (`/agents`, Planung + kritische Prüfung in `docs/ki-agenten.md`): Chat mit agentischem Loop über den Sammlungen. Konfiguration des Standard-Agenten unter *Verwaltung → KI-Agenten* (`ai_agents`, System-Agent = `SYSTEM_AGENT_ID`); Threads, Nachrichten und Thread-Konfiguration in `agent_threads`/`agent_messages`/`agent_thread_collections`/`agent_thread_instructions` (bewusst **nicht** `conversations`/`messages`). Der Loop läuft im **Worker** (BullMQ-Job `{kind:"agent-turn"}`, `src/server/agents/loop.ts`), streamt über `publishToUser` (`agent.message.*`, `agent.turn.finished`) und ist per Redis-Key `aiup-agent-cancel-<threadId>` abbrechbar. Werkzeuge als Registry in `src/server/agents/tools/` (zod-Schema, englisches `description`, `{de,en}`-Labels, `run()` gegen die Domänenschicht – **nie** gegen Server Actions); sie handeln immer im Namen des aufrufenden Nutzers, die Sammlungsauswahl kann Rechte nur einschränken. Zugriff wird pro Sammlung gewählt (leer = alle lesbar), Instruktionen pro **Eintrag** (deren Markdown landet im System-Prompt, Budget 40.000 Zeichen). Ohne eigenen Prompt gilt `DEFAULT_AGENT_SYSTEM_PROMPT` (`src/server/domain/agents.ts`). Harte Grenzen je Antwort: `maxSteps`, `maxTokensPerTurn`, `MAX_WRITES_PER_TURN` (10). Arbeitsmodus je Thread: `assist` (nur lesen) vs. `curate` (Schreib-Tools, Sammlungen einzeln freigeben). Bei `writeApproval: "always"` (Standard, Icon-Umschalter im Chat-Kopf) parkt der Loop jeden Schreib-Aufruf als Nachricht mit Status `awaiting_approval` (der Aufruf liegt dabei in `tool_calls`) und beendet den Zug; Zustimmung/Ablehnung reiht den Folge-Zug ein (`resolveToolCall`). Wochenkontingent je Nutzer (`app_settings.agentWeeklyTokenBudget`, `0` = aus; Verbrauch = Eingabe + Ausgabe × `agentOutputTokenWeight`, Reset montags in der App-Zeitzone, `src/server/agents/usage.ts` + `src/lib/week.ts`): geprüft beim Senden und zwischen den Loop-Schritten, Übersicht unter *Verwaltung → KI-Agenten*. Agenten-Schreibvorgänge tragen `origin: {kind:"agent"}` – Content-Trigger ignorieren sie, solange `includeAgentOrigin` aus ist, und die Eintrags-Bewertung wird gebündelt am Zug-Ende eingereiht statt je Speichern.
- Modell-Fähigkeiten (`llm_model_capabilities`, Planung in `docs/modell-faehigkeiten.md`): Werkzeuge, Reasoning-Stufen, strukturierte Ausgabe und Kontextgröße je Modell-Id (global, providerübergreifend – dasselbe Modell verhält sich bei jedem Gateway gleich). Nötig, weil `supported_parameters` eine OpenRouter-Eigenheit ist und die meisten OpenAI-kompatiblen Anbieter nichts über sich verraten. **Jede Spalte ist nullbar: `null` heißt „nicht angegeben", nicht „kann es nicht"** – dann greift der Rückfall. Auflösung in `src/server/llm/capabilities.ts` (`mergeCapabilities`, rein und getestet): Tabelle → `supported_parameters` → Heuristik nach Provider-Typ; `resolveModel()` liefert das Ergebnis als `caps` mit, `modelCapabilities()` ist nur noch der Rückfall. Reasoning ist eine **Liste** erlaubter Stufen (`none|low|medium|high|max`), weil die je Modell unterschiedlich sind (glm-5.2: `none|high|max`, gpt-oss-120b ohne `none`); `normalizeReasoningLevel()` verwirft eine konfigurierte Stufe, die das Modell nicht kennt, statt sie zu senden. Das Agenten-Formular bietet nur die hinterlegten Stufen an (ohne Eintrag nur „Aus" plus Hinweis) und `saveAgentAction` lehnt eine ungültige Stufe mit Meldung ab; der Workflow-Editor hat noch den festen Satz – zur Laufzeit greift dort dieselbe Prüfung. Gepflegt wird die Tabelle über MCP (`llm:read|write`: `list_model_capabilities`/`set_model_capabilities`/`delete_model_capabilities`, Resource `aiup://docs/model-capabilities`) – **Merge-Semantik**: weggelassenes Feld behält den gespeicherten Wert, `null` löscht ihn.
- Meetings: LiveKit-Glue in `src/server/meetings/` (`livekit.ts` Token/Raum/Webhook → Meeting-Status, `recording.ts` Audio-only-Egress + Import). Raumname = `m-<meetingId>`; Status/Teilnehmer kommen **nur** über den Webhook `/api/livekit/webhook` (public, signiert) und werden per Realtime `meeting.updated` verteilt. Integrations-Settings (URL/Key/Secret verschlüsselt) in `integrations`, Zugriff über `getLiveKitConfig()`; Aufzeichnungen liegen im gemeinsamen Host-Verzeichnis (`recordingsPath`, Container-Pfad `/data/recordings`). Lokal: `docker compose -f docker-compose.dev.yml --profile media up -d` (Dev-Keys `devkey`/`devsecret…`, Webhook auf `host.docker.internal:3000`).
- Shared Server-Code (`src/server/**`) darf nichts aus `next/*` oder React importieren, wenn er auch im Worker (`worker/`) läuft (Ausnahme: `react`'s `cache` in `domain/settings.ts`, Worker nutzt `loadAppSettings`); `server-only` nur in Next-spezifischen Modulen (z. B. `src/server/auth/session.ts`). BullMQ-Job-IDs dürfen kein `:` enthalten.
- Prüfen vor Abschluss: `npm run typecheck && npm run lint && npm run build && npm run worker:build`. Multi-User-Tests lokal: zweite Identität über `http://127.0.0.1:3000` (eigene Cookies).
